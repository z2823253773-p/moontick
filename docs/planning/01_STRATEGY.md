# MoonTick 全局策略

## 1. 产品定位

MoonTick 是一个 MoonBit 定频采样计划审计库，附带离线 CLI。用户声明“从什么时候到什么时候，每隔多久应该有一条记录”，系统核算应有与实有时间点，给出缺口区间、重复记录、乱序、离网格点和越界记录，并定位输入行。

首要用户：在 MoonBit 中处理固定时间桶、定频归档或批量数据导入的开发者。最终使用者也可以直接用 CLI 检查文件，无需编写 MoonBit 程序。

产品价值假设：把容易反复写错的时间边界和覆盖率逻辑变成有契约、可复用、可在 CI 阻断坏输入的组件。该假设需要 G0 的相邻包核查与后续真实试用验证，目前不能宣称已证明市场需求。

## 2. 为什么还值得做，以及何时不该继续

已发现 MoonSignalKit 提供时间间隔和迟到监测，MoonVerity 提供通用数据质量检查，MoonSplit 提供数据集划分与隔离审计。因此“MoonBit 没有数据检查工具”不是我们的理由。

独立价值假设是 **完整采样计划的核算**：

- 显式窗口才能发现数据开头、结尾缺失，以及完全无数据的预期序列。
- 覆盖率基于不同的有效网格点，重复行不能提高覆盖率。
- 缺口用网格索引区间压缩表示，巨大窗口不会导致逐点枚举。
- 库、CLI、批量检查使用同一套规则，结果可定位、可复现。

G0 必须检查相邻项目的 README、公开接口、实现或可运行例子，记录版本/commit 和证据。网页没写某功能，只能标“未验证”。

**继续条件**：两个有一手来源的真实问题/工作流，能映射为明确计划、输入、结果和处理决定；结合生态差异说明组件价值。开工前不要求已完成第三方接入。[需求证据卡](09_USE_CASE_EVIDENCE.md) 支持问题存在与用途合理性，独立 MoonBit 库的采用需求仍待试用验证。

**转向条件**：已有活跃项目完整覆盖这些需求；赛方认为选题过度重复；或启动验证显示主要时间都将用于补基础设施。Codex 给出“缩小并集成已有库 / 为已有项目贡献 / 更换选题”的具体建议，由你决定。不能擅自把已有项目的历史贡献算到自己名下。

## 3. 月度版本和季度版本

| 层次 | 交付边界 | 通过依据 |
|---|---|---|
| v0.1 月度验收 | 单序列、整数毫秒时间戳、固定网格、ticks 无表头行输入、五类问题、文本/JSON 报告、可复用库、CI | 契约测试、CLI 真实进程、发布包在独立消费者工程可用 |
| 季度主线 | 真实试用、独立消费者工程、修复与复现证据 | 可运行案例、反馈与版本改进；没有接入则如实记录 |
| 可选 v0.2 | 按反馈决定是否做显式多序列 manifest 与批量报告 | 若实施则验证缺席序列、隔离和旧版兼容 |
| 可选增强 | 完整 CSV / UTC RFC3339 适配、静态可视报告、其他后端或平台 | 用户反馈明确需要且核心与截止时间允许 |

首版不做自动修复、补值、统计异常检测、预测、实时服务器、数据库、账户系统。对任意事件流、交易日历、夏令时、可变频采样不宣称适用。季度新增功能也不能改变首版默认边界而不升级契约。

季度目标不是把五条检查扩展成几十条规则；优先提升可复用性、可信度和实际接入质量。

## 4. 季度竞争力的证据结构

以下是内部建设目标，不是主办方评分权重，也不保证获奖：

| 主张 | 要交付的证据 | 不足时怎么说 |
|---|---|---|
| 补足生态能力 | 版本固定的竞品矩阵、具体差异用例、集成理由 | 只能说候选差异，不能说生态首创 |
| 正确可信 | 小样本独立 oracle、生成式测试、边界回归、审查记录 | 单元测试通过不等于端到端通过 |
| 实际可用 | 从 registry 安装、干净环境运行、清楚的失败诊断 | 源码运行不等于发布包可用 |
| 持续建设 | 版本变更、真实 Issue、复现—修复—回归链条 | 不用空提交、伪用户或星标替代 |
| 具有复用价值 | 目标 2 位独立试用者、1 个独立消费者工程、3 个完整用例 | 招募失败如实报告，不虚构评价 |
| 本人掌握项目 | 你现场解释边界、演示坏例子并回答设计取舍 | 不把模型输出当作自己已理解 |

如果外部试用难以获得，至少让同学在干净机器仅凭 README 完成安装、运行和定位一个错误；准确标注为复现测试，不包装成真实生产采用。

## 5. 两个有来源的用途与一个边界演示

1. 定频公共归档导入审计：按分钟计划核算缺行区间，调用方决定重拉或记录缺失政策。来源为 Binance 官方仓库 issue #483；本包仅做合成最小复现，没有重新下载验证其原始档案。
2. 时间桶导出交付检查：提供由计划独立驱动的缺席核算；来源为 Flux issue #3428 和官方文档。默认桶终点标记要显式处理，示例选用桶起点，避免把时间错位误判为丢失。
3. 全缺席/重复冒充完整：纯合成契约演示，不称为第三个已验证需求。

完整证据与限制见 [09_USE_CASE_EVIDENCE.md](09_USE_CASE_EVIDENCE.md)。抖动原始时间戳或业务不要求稠密时间桶的场景不直接适用。

## 6. 阶段和时间安排

2026-09-21 起按放行时点滚动排程。9/24 仅作内部检查点；G0 记录官网写 9/30，精确申报/验收时间待确认。第一赛季度 8—10 月不等于已知材料截止。

| 阶段 | 工作 | 完成门槛 |
|---|---|---|
| 当前 G0-R | 范围、需求证据、工具链方案 | 文档一致，下载/安装未决项有记录 |
| 获准启动后的首个开发时段 | 工具链与最小闭环 | 文件→核心→JSON→真实退出码 |
| 随后 1—2 个开发时段 | 完整核心、行输入、独立比对 | 边界、精度、空序列、资源用例成立 |
| 再后 1—2 个开发时段 | CLI、CI、发布准备与安装复现 | 平台证据、包内容和 README 一致 |
| 验收后 | 试用、修复、消费者工程 | 真实反馈与回归 |
| 季度阶段 | 按需求选择 T7，完成 T8 | 复现案例、贡献和维护记录 |
| 官方截止前至少 5 天 | 冻结、排练与核对 | 按明确官方日期倒排 |

开发时段是工作分组，不是数日交付保证。若闭环或规则确认延误，核实下一期能否进入本季度，不能自行承诺延期。有效 commit 与人工申报按当前规则执行，不能靠空提交赶进度。

## 7. 你的投入与决策

默认每天 2 小时：约 20 分钟看状态与阻断项，40 分钟学懂/复现当前核心行为，30 分钟核对反馈和任务优先级，30 分钟处理申报/社区与演示。时间不足时先削减可选增强。

你保留的决策：选题是否继续、语义是否变更、重大范围扩张、官方规则答复、发布与提交。任务内修复、补测试、更新文档由执行工具自主完成。

AI 时间策略：每轮完成一个可验收任务；出现核心语义争议先写出最小反例；同一失败尝试两次仍无新证据就改变调查方法。避免两边反复全文重读、循环互审或同时重构。

## 8. 本人应能回答的五个问题

1. 为什么固定记录数量不足以证明数据完整？
2. 为什么一定要用户提供起止时间，不能仅从文件首尾推断？
3. 一条记录可以同时属于重复和越界吗？为什么？
4. 十亿个预期时间点但只有十条记录时，为什么不会创建十亿个对象？
5. Python 在项目里做什么，实际审计逻辑在哪里运行？

答案必须能在规格、代码与演示中一致地找到。
