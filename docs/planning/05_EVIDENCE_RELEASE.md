# 验证、试用、发布与季度展示

## 1. 证据分类

统一在 `docs/evidence/` 下记录。每条证据包含日期、任务、操作系统/工具链、被测 SHA、命令、退出码、输出路径、结论和限制。状态只用 PASS / FAIL / NOT_RUN / BLOCKED；NOT_RUN 不能算 PASS。

| 类型 | 能证明什么 | 不能证明什么 |
|---|---|---|
| 单元测试 | 函数对固定用例符合预期 | 真实文件/CLI 一定可用 |
| 独立差分 | 小样本与不同方法的参考结果一致 | 所有输入、所有平台绝对正确 |
| CLI 测试 | 真实进程、输出和退出码符合契约 | Mooncakes 发布包可安装 |
| CI | 指定提交在指定远程环境通过 | 本地最新未提交改动通过 |
| 干净安装 | 指定已发布版本被外部消费者使用 | 所有用户和平台适用 |
| 真实试用 | 某个具体用户/场景可用或发现问题 | 大规模采用或商业成功 |
| 官方回执 | 报名/审核/验收/季度资格的对应状态 | 其他阶段自动通过或必定获奖 |

所有数字附环境与方法，不能只贴截图而没有命令和输入。报告引用相对路径；公开文档脱敏主机用户名、私有路径和身份信息。

## 2. 测试矩阵

| 组别 | 必须覆盖 | 优先级 |
|---|---|---|
| 网格 | 半开端点、负数、整周期、零/负步长、反向窗口、溢出 | 月度阻断 |
| 核心 | 正常、头尾缺失、连续缺口、全缺失、重复、乱序、离网格、越界及重叠 | 月度阻断 |
| 解析 | 空文件/空行、LF/CRLF、末行无换行、BOM/非 ASCII/表头拒绝、规范整数 | 月度阻断 |
| CLI | help/version、缺参数、重复/未知参数、实际退出码、stderr/stdout | 月度阻断 |
| 报告 | JSON 可解析、Int64 精度、稳定排序、行号、truncated、精确计数 | 月度阻断 |
| 资源 | 十亿以上网格点不展开、输入/token/行数上限、超时、不隐式截断 | 月度阻断 |
| 独立 oracle | 至少 1000 个固定种子小案例、手工金标准、变形性质 | 月度内部质量目标 |
| 安装 | 源码和发布包两条路径；外部工程从 registry 导入 | 发布阻断 |
| 批量 | 缺席序列、未知/重复 ID、隔离、聚合限额、旧版兼容 | 仅在实施 T7 后阻断 |

不以测试条数替代真实行为覆盖。构建通过、覆盖率高或两个模型都认可，都不能消除已存在的反例。

## 3. 每次候选版本的检查

在所选工具链确定后，执行并保存实际命令；命令不支持时先查该版本帮助，不静默跳过。

```bash
moon version --all
moon fmt --check
moon check --target native
moon build --target native
moon test --target native
moon info
```

接着执行 T4/T5 创建的真实 CLI 和差分测试。`.mbti` 与已提交公开接口是否一致用 Git diff 检查；编译器升级导致变化，要审查而不是忽略。

证据页至少记录：产品版本/测试 SHA，操作系统、CPU、Moon/moonc、依赖，单元/CLI/差分/CI/包安装分别的状态及证据位置，未覆盖平台与限制，阻断缺陷，公开主张对应的可复现证据。这是记录结构，不是已发生的通过结果。

## 4. 性能与资源测量

区分记录数 m 很大和预期网格 N 很大，分别测量。

- 固定 N=10^12、m=2，检查输出仍仅一个缺口区间，证明不会枚举 N。
- m 从 1,000、10,000 到 100,000，再到上限 250,000；分别用正常、重复、乱序和密集缺口样本。
- 每组先预热一次，再记录五次的中位耗时及观测到的峰值内存。写 CPU、系统、编译模式、命令和输入哈希，不比较不同机器裸数字。
- 包含超上限的拒绝测试。不得提前宣称速度/内存数字；实测后再决定有依据的性能预算。

## 5. 试用与维护

内部目标：两位独立试用者、一份独立消费者工程、三个完整场景。由你邀请或在明确授权后联系，AI 不自动私信别人。

试用者收到 README、版本、合成或许可清楚的数据、一项具体任务。让对方记录：能否独立安装、哪个输入不理解、诊断是否定位到问题、结果与手算是否一致。

记录字段：试用编号/日期/版本/环境/数据来源；试用者公开昵称或匿名编号（经其同意）；具体任务；实际观察；复现输入/命令/结果；Issue、修复 SHA、回归用例；是否重试；公开引用许可。

没有反馈就记录没有；开发者本人运行不能算外部试用。对外发布 Issue/请求协作按已有授权执行，不用虚构账号制造社区活跃。

## 6. 发布检查

先完成可审查的候选包，再处理最终对外动作。已经明确授权的动作无需重复确认。

准备确切 repo/命名空间、版本与 SHA、许可证、依赖/参考清单、包内容、测试/CI 状态、README/CHANGELOG、已知限制和安装步骤。

- 包内无令牌、凭据、身份证、银行卡、学籍文件或私有业务数据。
- 样本都是合成或许可可公开数据，不引入科研/临床原始数据。
- README 只声明实际验证的平台和后端。
- 实际执行 `moon publish --dry-run` 并检查输出；它不是发布回执。
- 正式发布后查 registry 的真实包/版本；独立工程安装该版本验证。
- 不覆写旧 release 或移动已公开标签来掩盖错误；修复用新版本说明。

身份材料由你本人通过官方表单处理，公开仓库只留脱敏状态。报名承诺由你阅读并接受。

## 8. 季度展示

准备 5 分钟和 10 分钟两个版本，不预设官方时长。

5 分钟：40 秒用“记录数够但有重复和缺口”说明问题；60 秒说明显式计划、首尾缺失与缺席序列；90 秒现场跑正常/坏例子并定位原始行；60 秒展示独立验证、安装和一个真实修复链条；50 秒说明相邻项目、本届贡献及限制。只展示实际实现的能力。

10 分钟：增加库接入、复杂边界、性能方法和反馈驱动改进。准备离线录屏备用并标录制版本，不伪装成现场运行。

讲述材料可由 AI 协助整理，但由你核验；正式申报书遵循人工撰写要求。重点是软件解决什么问题、为何可信、谁用过。

## 9. 最终交付清单

- 公开仓库、实际 Mooncakes 包/版本、候选 SHA。
- 安装说明、三个场景、API/CLI 参考、输入输出契约、限制。
- 单元/独立差分/CLI/CI/安装的证据索引。
- 竞品差异、参考来源、许可证、本届贡献。
- 真实反馈和修复链条；没有则说明不足。
- 演示脚本、备份材料、官方要求的材料和回执。

只有证据真正产生后，才把相关任务标为 DONE。
