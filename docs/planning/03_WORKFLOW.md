# Codex × Claude Code 协作协议

## 1. 角色

| 角色 | 主要责任 | 每轮交付 |
|---|---|---|
| 你：参赛者/产品负责人 | 理解需求、确认重大取舍、答复规则问题、人工写申报书、最终发布/提交决策与演示 | 决策、官方回执、真实试用反馈 |
| Codex：技术负责人/独立验证 | G0 调研、契约维护、拆任务、独立 oracle、恶劣输入与集成测试、代码审查、证据审核 | 可复现问题或带 SHA 的审查结论 |
| Claude Code：主要实现者 | 实现当前任务、开发测试、行输入/CLI/CI、文档和示例、修复审核发现 | 可运行改动、验证日志、变更说明、交接状态 |

不指定某家模型天生更可靠。可靠性来自职责和独立验证。如果 Claude Code 因额度/环境中断，Codex 可以接替实现，但要明确角色切换，并由另一个工具做该任务的最终独立复核。

## 2. 默认协作方式：顺序接力

对单人、小项目，默认一名代码写入者。不要让两个工具在同一工作目录同时写文件或运行会改变生成文件的命令。

```text
你确认目标/范围
      ↓
Codex：发出任务卡（输入、接口、例子、完成标准）
      ↓
Claude Code：实现 → 自测 → 提交 → 交接
      ↓
Codex：在该 SHA 上独立运行测试 → 审查
      ├─ 有问题 → 最小复现 → Claude 修复 → 复查改动及回归
      └─ 通过 → 更新状态 → 下一任务
      ↓
候选版本 → 干净安装 → 证据包 → 你授权发布/正式提交
```

审查是自动推进工作的技术门槛，不是每张任务都让你重新批准。通常只有选题/语义/大范围变化、无法从现有信息判断的业务问题，以及未获授权的外部动作需要你介入。

## 4. 单轮任务卡

一个任务通常控制在一轮可审查改动。复杂卡拆小，但不要靠碎片化增加提交数。

```text
任务：Tn / 标题
基线：分支、commit SHA、工作目录
目的：用户能得到什么行为
本轮读入：规格章节、上游文件/接口
允许修改：具体目录/文件
交付：函数/命令/报告和错误行为
验收：给定输入、预期输出、运行命令、成功/失败标准
明确边界：本轮不扩展的功能
证据路径：docs/evidence/Tn/...
实现者：Claude Code；复核者：Codex
```

## 5. 每次交接的最小内容

在 `.ai/TASK_STATE.md` 保留当前状态，不写成长对话记录。较长证据放 `docs/evidence/`，设计取舍放 `docs/decisions/`。

```text
任务编号和状态：READY / IN_PROGRESS / REVIEW / DONE / BLOCKED
active_owner：Claude Code / Codex / user
repo_root、branch、tested_commit
完成了什么；明确没有完成什么
修改文件和原因
运行命令、退出码、日志路径、环境版本
仍失败/未运行的检查
当前阻断与需要谁提供什么
下一步唯一优先任务
```

审查不能只写“LGTM”。每条发现应有：严重度、文件/行为、最小输入、实际结果、规格要求、建议修复方向。无法复现的担忧标为待验证，不当作已证实缺陷。

证据的 SHA 指向被测代码。若后续提交只新增报告，记录“测试 SHA”和“报告提交 SHA”分别是什么；产品/测试/依赖改动后必须重新测试，不复用陈旧通过标记。

## 6. 冲突、中断与恢复

- 规则冲突：以用户明确指令和当前官方确认优先，再到已冻结规格、任务卡。不能拿旧记忆代替当前文件。
- 技术分歧：先构造最小反例，查规格与权威文档，再选方案；涉及产品语义才交给你决定。
- 网络失败：记录实际错误；继续纯离线实现和验证。网络失败不得记作发布成功或 CI 成功。
- 工具额度中断：先保存改动、证据与下一命令，再交接。新会话只读启动文件和当前任务材料，不重新做全部规划。
- 未获得赛方日期答复：9/24 仅作内部检查点，继续已获授权的本地工作；季度资格和最终提交状态保留“未确认”。
- 验证失败：先确定是实现错误、环境问题还是规格歧义，再修复；不能删掉失败用例或修改 expected 来掩盖问题。

## 7. 上下文预算

每轮先读 AGENTS、TASK_STATE、当前任务和相关规格章节。除非发现范围变化，不反复全文读全部材料。让实现者输出必要证据，审查者复核关键路径，避免重复运行同一套已通过且未受改动影响的检查。

月度版本优先顺序：正确性 → 可运行闭环 → 验收要求 → 文档可读性 → 性能测量 → 可选展示。季度版本在此基础上增加真实接入与维护；先收集反馈再排新功能。
